Limit order book · Java

System Architecture

How the pieces fit together: six named threads plus a virtual thread per HTTP request, four boundaries between them, and one rule that explains nearly every design decision - the order book is touched by exactly one thread, and nothing but immutable values ever crosses from it to another.

The pipeline

producer thread matcher thread trade writer thread main thread http virtual threads strategy thread requote thread thread boundary

Three listeners run on the matcher thread, in that order: audit first, so a trade is on disk before anything downstream can throw; display second; strategy last, and only ever offer, so it can never hold the matcher up.

The threads

ThreadCreated byOwnsHow it stops
main the JVM the renderer, and the wiring of every object falls off the end of main()
producer OrderFlowDriver.start() MidPriceWalk, MarketDataGenerator flag and interrupt() - the flag alone cannot reach a thread parked in put()
matcher OrderGateway.start() OrderBook, every PriceLevel, every resting Order a queued Shutdown command, so the backlog drains first. Offered with a timeout, not put(), so a full queue cannot make shutdown hang; interrupt is the last-resort fallback
trade-writer TradeLogger.start() the BufferedWriter on trades.csv a queued Shutdown command, for the same reason: it owes the backlog it accepted
one virtual thread per HTTP request BookFeedServer's executor nothing. It reads a published snapshot and shares no state at all server.stop(1), then the executor is closed - which HttpServer.stop does not do for you
strategy StrategyRunner.start() the strategy's position, its live quote ids and its P&L a queued Shutdown command, so the fills it owes its position are delivered first - and stopped before the gateway, so its last cancels still land
requote RequoteScheduler.start() nothing. It only asks the strategy to replace its quotes shutdown() then awaitTermination. Stopped first of all, so no new tick arrives part-way through a shutdown

The shutdown mechanisms differ because the threads differ. A consumer has already accepted work it owes, so it must be stopped in order, by a sentinel that arrives behind the last real item - which is why both the matcher and the writer take a queued Shutdown command. A producer owes nothing yet and may be stopped immediately - and must be, since nothing feeds it, so no sentinel could ever reach it. Hence the producer is interrupted and the consumers are not.

Order matters at both ends. Start inwards-out, each consumer before whatever feeds it: trade log, gateway, strategy, driver, feed server, requote clock. Stop in the exact reverse, so nothing is still submitting to a component that has already closed.

Life of one order

  1. producer threadPriced. MidPriceWalk.next() nudges the mid one tick; the generator picks a side, offsets the price by a signed amount, and draws a size and an account. The offset is signed on purpose: it makes roughly half the flow aggressive, which is the only reason any trade ever happens.
  2. producer threadHanded over. gateway.submit(order) puts it on the queue and returns. If the queue is full the producer blocks here, and is paced by the matcher instead of by its own delay. That is back-pressure, not a bug.
  3. matcher threadTaken. matchLoop pulls it off. From here until step 6 nothing else in the system can touch the book.
  4. matcher threadMatched. The engine walks the opposite side best-price-first, filling while the prices cross, emitting a Trade per fill at the resting order's price. Fully filled resting orders are removed.
  5. matcher threadRested or discarded. An unfilled limit remainder joins the back of its price level; a market remainder is cancelled.
  6. matcher threadReported. The gateway calls the MatchListener with the order and its trades, then counts both. One listener, composed with andThen, so two things happen in a fixed order: the audit log first, the display second. If the display throws, the trade has already been recorded.
  7. matcher threadQueued for audit. TradeLogger.onMatch offer()s each trade and returns. It never blocks and never touches the disk, because the matcher is waiting on it.
  8. matcher threadPublished. The second listener builds a BookSnapshot - legal, because it is running on the matcher thread - and set()s it on the atomic reference along with the running counts.
  9. trade-writer threadWritten. The writer takes the trade, appends one CSV row, and flushes whenever it has caught up. Slow I/O, off the hot path.
  10. main threadRendered. The renderer reads the latest snapshot and redraws, five times a second. It never sees the book.
  11. a virtual threadServed. Independently, any HTTP request for /book reads that same reference, converts it to a MarketDataSnapshot and writes JSON. Many requests can run at once precisely because the value they read cannot change under them.

Steps 7 to 9 are three readers of one write. Adding the HTTP feed needed no change to the matcher at all, which is the practical payoff of publishing immutable values instead of sharing a structure.

Packages

com.mwang.model

  • Order - an entity: identity outlives state, so a class, not a record. One mutable field, remainingQuantity. Prices are scaled long ticks, never double.
  • Trade - a value: immutable record, priced at the resting order's price.
  • OrderIdAllocator - one shared AtomicLong, drawn on by every participant submitting to the same book. A book rejects a duplicate id while the first order still rests, so sharing one sequence makes collision impossible where separate bases only make it unlikely. The one place in the project where the atomicity is load-bearing rather than defensive: two threads really do draw at once.
  • Side, OrderType - enums.

com.mwang.book

  • OrderBook - two TreeMaps (bids reversed, asks natural) plus a HashMap index for O(1) cancel. Not thread-safe, by design.
  • PriceLevel - an ArrayDeque; the queue is the time priority, which is why colliding timestamps are harmless.
  • DepthLevel, BookSnapshot - immutable views. The snapshot is the only thing permitted to leave the matcher thread.

com.mwang.engine

  • MatchingEngine - the abstraction, so a pro-rata policy could drop in.
  • PriceTimeMatchingEngine - price-time priority, trades at the resting price, limit remainder rests, market remainder cancels, self-trades reject the incoming order.

com.mwang.gateway

  • OrderGateway - the thread boundary. Many producers may call submit(); exactly one thread ever reaches the engine.
  • MatchListener - the way results escape the matcher. Runs on the matcher thread, so it may read the book but must be fast, and anything it throws is caught so a broken listener cannot kill the exchange.

com.mwang.marketdata

  • MidPriceWalk - bounded random walk, seeded, clamped so the mid stays positive.
  • MarketDataGenerator - one mid becomes one order. Rejects a single account, because self-trade prevention would then reject every match and nothing would ever trade.
  • OrderFlowDriver - owns the producer thread and its pacing.

com.mwang.audit

  • TradeLogger - a MatchListener that is also a thread owner. Queues on the matcher thread, writes on its own. Uses offer() rather than put(), because the matching engine is not a caller that can be made to wait; drops are counted, logged and reported at close, never silent. This is the opposite trade-off from the gateway, and deliberately so.

com.mwang.feed

  • MarketDataSnapshot - the published wire format. Separate from BookSnapshot so the book package stays free of serialisation concerns, and so the -1 empty-side sentinel reaches consumers as null rather than as a price of minus one cent. Component order is the JSON field order, so a test pins the exact string.
  • BookFeedServer - GET /book over the JDK's own HttpServer. Takes a Supplier, not the book, so it cannot reach matcher-owned state even by mistake.

com.mwang.strategy

  • Strategy / QuotingStrategy - onFill(Trade) and onRequote(), both called on the strategy thread. A strategy holds its own gateway and snapshot supplier, so these interfaces pass neither and the runner stays free of any opinion about trading.
  • StrategyRunner - the MatchListener that makes the above safe. Its onMatch runs on the matcher thread and does nothing but offer a fill onto its own queue. A strategy quoting directly from onMatch would have the matcher adding two quotes for every order it removes, filling the queue it alone drains until put() blocks it permanently - a cycle rather than a chain. A test reproduces that shape and times out, to prove the guard works.
  • Command - Fill, Requote or Shutdown, sealed. A sentinel Trade reaching a strategy would be booked as a real execution and corrupt its position silently, which is the sharpest reason of the four queues to type the signal.
  • RequoteScheduler - a one-thread ScheduledExecutorService on a fixed delay, not a fixed rate: after a pause, a fixed rate runs every missed tick back to back, each one cancelling and reposting both quotes for the same resulting pair. Its task catches RuntimeException, because a throw escaping a scheduled task cancels the schedule silently and the strategy would simply stop quoting.
  • Position - signed quantity and a cost basis rather than an average price, which would truncate on every fill. Realises P&L on whatever a fill closes; unrealised is marked against a mid.
  • SimpleMarketMaker / AdaptiveMarketMaker - a fixed half-spread, and one scaled to measured volatility. Both skew their centre against inventory and withhold a side at the position limit. README.md has the measurements for why the fixed one loses money.

com.mwang · com.mwang.sim · com.mwang.exception

  • SimulationRunner - wires everything, starts forwards, stops backwards. Owns the AtomicReference and the listener lambdas that write to it; every component below it stays unaware of the others. The construction order is circular - the maker needs the gateway, the gateway needs its listeners, one listener is the runner, the runner needs the maker - and the notifyStrategy lambda is what breaks it, because a lambda body does not run when the lambda is built.
  • SimulationConfig / SimulationResult / StrategyFactory - the parameters in, the figures out, and which strategy to quote with. A factory rather than another config field, because each strategy takes different parameters.
  • ConsoleRenderer - every frame the same height, so redrawing over the previous one cannot tear.
  • Main - one line: a config and a strategy.
  • OrderException and its two subtypes - business rejections the gateway catches and logs, as distinct from programming errors, which are left to crash.

The rules behind the shape

Single writer

One thread owns the book. No locks on the matching path, no contention, and the order of execution is fixed - which is what makes the engine deterministic, a regulatory requirement for a real exchange and a testable property here.

Confinement, not synchronisation

OrderBook has no locks because nothing shares it. The cheapest way to make shared state safe is for it not to be shared. Code that needs to read it runs on the owning thread, as the listener does.

Only immutable values cross

Orders go in through a queue; snapshots come out through an atomic reference. Neither direction ever passes a mutable structure between threads, so neither needs a lock.

Never feed a queue you alone drain

The matcher must not put() onto its own inbound queue. Doing so - via a listener that submits - adds more per cycle than it removes, fills the queue, and blocks the one thread that could free a slot. That is why strategy code runs on its own thread and reaches the matcher only through the queue, and why the audit log offers rather than blocks. A chain, never a cycle.

Control signals are typed, not faked

All three queues carry a sealed Command - Submit/Cancel/ Shutdown, Append/Shutdown, Fill/Requote/Shutdown. Shutting a consumer down needs a sentinel that arrives in order behind real work; using a fake Order or Trade with values chosen to satisfy a validator puts a bogus execution one missed identity check away from the book. A sealed case is checked by the compiler, and the exhaustive switch means a fourth instruction cannot be silently ignored.

Slow work belongs off the matcher

Building a snapshot takes nanoseconds and happens on the matcher thread. Drawing it to a terminal, appending it to a file and serialising it to JSON all take orders of magnitude longer, and all happen somewhere else. The trade log is the clearest case: the listener offer()s to a queue in nanoseconds and the writer thread does the I/O.

The same reasoning sets the log levels. Logback's appenders are synchronous, so a per-trade INFO line would put file and console I/O back on the matcher thread - undoing the whole arrangement. Trades log at DEBUG; INFO carries lifecycle and run totals.

Back-pressure over dropping

A bounded queue plus a blocking put() means a fast producer is slowed to the matcher's rate rather than exhausting memory. A real exchange would instead offer() and reject, because it cannot let a slow matcher stall its network threads - but it must never silently drop.

Which to use depends on who is calling. At boundary 1 the caller is a client, who can wait, so blocking is right. At boundary 2 the caller is the matching engine, which cannot, so offer() is right and the rare drop is counted and reported. Same queue type, opposite decision, because the question is never "block or drop" in the abstract.
