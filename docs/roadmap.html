Matching Engine Roadmap

A five-phase build plan for a limit order book and matching engine in Java, written to prepare for the IMC Trading internship. Each phase layers on new language and concurrency concepts on top of a working system — nothing is thrown away between phases.

00

Environment & tooling setup

0.5–1 day

Get a project scaffold running end to end before writing any real logic, so every later phase starts from a known-good baseline.

  1. Install JDK 25 via sdkman install java 25-tem (or the Adoptium installer on Windows), and confirm with java -version.
  2. Install IntelliJ IDEA Community Edition and create a new Maven project: groupId com.mwang, artifactId matching-engine.
  3. Set maven.compiler.release to 21 or higher in pom.xml so records, sealed interfaces and pattern matching are available.
  4. Add junit-jupiter and assertj-core as test-scope dependencies.
  5. Initialise Git, add IntelliJ's generated .gitignore plus target/, and push an empty repo to GitHub.
  6. Write a placeholder Main class and one trivially-true JUnit test, run both from IntelliJ's gutter icons, and commit as "Project scaffold".

Definition of done

A GitHub repo with a green build, a passing placeholder test, and a two-line README describing what the project will become.

01

Core order book

4–6 days

Model resting orders and price levels correctly before any matching exists. This is where most of Java's "basics" actually live.

classes vs recordsenumsgenerics TreeMap / ArrayDequeencapsulationJUnit basics

Build steps

  1. In a model package: a Side enum (BUY, SELL), an OrderType enum (LIMIT, MARKET), a Trade record (immutable — buyOrderId, sellOrderId, price, quantity, timestamp), and an Order class rather than a record, since its remaining quantity mutates on partial fills. Store price as a scaled long (e.g. cents), never a double — this is worth understanding properly, since floating-point money bugs are a classic interview topic.
  2. Build a PriceLevel class wrapping an ArrayDeque<Order> as a FIFO queue at one price, exposing add, remove and total resting quantity.
  3. Build the OrderBook: a TreeMap<Long, PriceLevel> for bids (best = highest price) and one for asks (best = lowest price), using the map's natural and reverse orderings.
  4. Implement addOrder, cancelOrder, bestBid(), bestAsk(), and depth(int levels) for a snapshot view.
  5. Write OrderBookTest: orders resting at multiple price levels, best bid/ask correctness after inserts and cancels, and FIFO order preserved within a level.
  6. Add a small Main that builds a book from a hardcoded list of orders and prints its depth — your first visibly "working" milestone.

Definition of done

An order book that stores, cancels and displays resting orders with correct price-time priority, backed by passing tests.

02

Matching logic

5–7 days

Turn a passive book into an engine that actually crosses orders and produces trades.

interfacesstrategy patterncustom exceptions defensive validation

Build steps

  1. Define a MatchingEngine interface with List<Trade> submit(Order incoming).
  2. Implement PriceTimeMatchingEngine: on an incoming buy, walk asks from the best price upward while incoming.price >= ask.price, filling FIFO within each level, emitting Trades, and resting any unfilled LIMIT remainder on the book.
  3. Handle MARKET orders — match against the best available liquidity regardless of price, and decide (and document) what happens to an unfilled remainder.
  4. Add unchecked InvalidOrderException and UnknownOrderException (for cancelling a non-existent id), and be ready to justify why unchecked over checked here.
  5. Add self-trade prevention: reject or cancel the resting order when the incoming and resting orders share an account id.
  6. Extend the test suite with a hand-checked scenario table: full fill, partial fill, a marketable limit crossing multiple price levels, an unfilled market order, and self-trade prevention.
  7. Extract a MatchingStrategy interface behind PriceTimeMatchingEngine even though you'll only ship one implementation now — it sets up the pro-rata stretch goal later without a rewrite.

Definition of done

The engine crosses orders and produces trades that match a scenario table you've hand-verified in the test class.

03

Concurrency

6–8 days

Add concurrent order intake without letting it corrupt the correctness you just proved in Phase 2 — this is the phase interviewers will probe hardest.

BlockingQueuevirtual threadssingle-writer principle determinism testingJMH

Build steps

  1. Keep PriceTimeMatchingEngine single-threaded for determinism — this mirrors how real matching engines are built — and put concurrency at the ingestion boundary instead.
  2. Build an OrderGateway: producer threads (simulated clients) push onto a LinkedBlockingQueue<Order>; one dedicated matcher thread drains it sequentially into the engine.
  3. Use Executors.newVirtualThreadPerTaskExecutor() for the simulated client producers, to practise the concurrency model modern Java trading systems increasingly lean on, while the matcher itself stays a single platform thread.
  4. Add graceful shutdown (a poison-pill order or ExecutorService.close()) and a CountDownLatch to know when a simulated batch has fully drained.
  5. Write the determinism test: submit the same N orders both sequentially and concurrently from multiple threads, and assert identical trade counts and fill totals. This single test is the most valuable one in the project — it proves the concurrent wrapper hasn't broken the engine underneath.
  6. Stretch: benchmark queue submission latency with JMH across LinkedBlockingQueue, ArrayBlockingQueue and a ConcurrentLinkedQueue with your own backpressure logic.

Definition of done

Multi-threaded order intake feeding the single-threaded matcher, with a passing test proving concurrent and sequential runs produce identical results.

04

Market data & persistence

5–7 days

Feed the engine from something resembling real market data, and give it a way to report what it's doing.

streams / lambdasNIO.2Jackson try-with-resourcesSLF4J / Logback

Build steps

  1. Write a MarketDataGenerator producing a synthetic bounded random-walk mid-price, and submit orders around it into the Phase 3 gateway.
  2. Alternatively, parse a small historical tick CSV with Files.lines() and streams into a List<MarketTick>, then replay it at accelerated speed with a ScheduledExecutorService.
  3. Add a TradeLogger that appends every executed Trade to a file with try-with-resources and a BufferedWriter, flushed safely under concurrent producers.
  4. Add Jackson to serialise a BookSnapshot (best bid/ask, depth) to JSON, and expose it over a minimal com.sun.net.httpserver.HttpServer endpoint — enough of an API to poll without pulling in a full framework.
  5. Replace System.out.println with SLF4J + Logback: info-level on trades, warn-level on rejected orders, console and rolling-file appenders configured in logback.xml.

Definition of done

A runnable simulation that logs trades to a file and exposes live book snapshots as JSON, driven by synthetic or replayed data.

05

Market-making strategy

5–7 days

Tie every earlier phase together into something that resembles what IMC actually does, with a strategy quoting against your own book.

functional interfacescompositionScheduledExecutorService basic P&L

Build steps

  1. Define a Strategy functional interface: void onMarketData(BookSnapshot snapshot, OrderGateway gateway).
  2. Implement SimpleMarketMaker: quotes a two-sided spread around the current mid-price at a configurable half-spread and order size.
  3. Add a Position class tracking net quantity and realised/unrealised P&L as the strategy's own trades come back from the engine.
  4. Add a risk limit: once |position| exceeds a configured maximum, widen the spread or stop quoting entirely — this is the single most "IMC-flavoured" piece of the whole build.
  5. Requote on a fixed interval with ScheduledExecutorService, cancelling and replacing stale quotes rather than leaving them resting indefinitely.
  6. Write a SimulationRunner tying Phases 1–5 together end to end, printing a running summary of fills, position and P&L at the end of a timed run.

Definition of done

A self-contained simulation that runs for a fixed duration and prints a coherent P&L summary for a market maker quoting against your own engine.

Stretch goals

Only worth doing once Phases 1–5 are solid — none of these are needed to call the project finished.

  • A minimal front-end with Javalin (much lighter than Spring Boot for this scale) streaming live book depth to a browser page over a WebSocket.
  • A Dockerfile so the whole simulation runs from one docker run.
  • A GitHub Actions workflow running mvn test on every push — real CI experience for the repo.
  • A second MatchingStrategy implementation (pro-rata allocation) behind the Phase 2 interface, to prove the abstraction actually holds under a second use.
